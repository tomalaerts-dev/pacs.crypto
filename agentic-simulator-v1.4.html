pacs.crypto · v1.4 · agentic authorisation

When an AI agent initiates a payment — what the API checks, and what it cannot

pacs.crypto does not re-invent agent identity or mandates. Those are consumed from GLEIF's vLEI and Google's AP2. What this family adds is the ISO 20022 payment-instruction binding and the compliance trail — the layer that checks an agent's action against a principal-signed mandate, carries the facts that must travel with the transfer, and makes agent activity visible to supervisors. This walkthrough makes that binding tangible.

01Three layers — who owns what

consume

Identity & attestation

Who the agent is, bound to a real legal entity. GLEIF vLEI delegated identifiers; Visa TAP / Mastercard agentic tokens / DIDs. We reference and verify against it — we do not attest identity ourselves.

consume

Authority / mandate credential

What the agent may do, signed by the principal. AP2 Intent Mandate (a verifiable credential) or GLEIF Agent Mandate Credential. We reference and verify it — we do not issue mandates.

pacs.crypto

ISO 20022 payment-instruction binding + compliance

The piece both layers above explicitly leave open. We bind the verified mandate to an ISO 20022 payment, check the action against the mandate's scope, carry Travel Rule data, and disclose agent activity to supervisors.

Why this split matters. GLEIF's own paper names the "PSP-side verification interface at the payment instruction layer" as the critical missing piece, and invites complementary work rather than competing formats. That interface is exactly what this binding is.

02The mandate grants action classes, not a blanket permission

A mandate does not say "this agent may transact." It says "this agent may perform these classes of action, each within these limits." A principal can authorise an agent to pay but never to amend a limit; to move liquidity but never to raise an investigation. The VASP check is two-level: is this action's class authorised at all, and is it within that class's constraints?

INITIATE_PAYMENT

Max amount, allowlisted counterparties (LEI preferred), permitted chains/tokens, escalation threshold, multi-agent approval, execution gates.

MANAGE_LIQUIDITY

Max transfer amount, allowed accounts, escalation threshold. Value-like, so real constraints apply.

AMEND_LIMIT

A ceiling on how high the agent may set a limit — an agent that can change limits must not be able to raise one without bound.

RAISE_INVESTIGATION

Usually minimal or no constraints — raising an investigation moves information, not value, so it is disclosure-level.

04What travels, and what a supervisor can later ask



  
Travels with the transfer
The Travel Rule record gains an
  initiating_ai_agent block: which agent, on whose authority,
  human present or not. On stablecoin rails there is no bank in the middle to supply this — so it
  must ride with the transaction.

  
Reaches the supervisor
The regulatory report carries the same facts as a
  first-class, filterable dimension. A compliance officer can ask: "show me fully-autonomous
  agent payments over 250,000" — agent id, human-present and amount are all reportable.





05What the binding honestly cannot do



  
limit
    
It cannot tell whether a payment is hallucinated
The agent may be authorised and the
    facts stale. Execution gates (new beneficiary, post-gap, deviation) catch some cases; N-of-M
    independent-agent approval catches more. Neither is a guarantee.

  
limit
    
It cannot verify the agent understood the user's intent
"100 Lamborghini cars"
    vs "100 Lamborghini outboard motors" is resolved in the user's own agent interface, upstream.
    The binding only carries a reference to the intent artifact, so the payment can be
    reconciled against it afterward.

  
limit
    
It cannot prove reasoning independence
N-of-M signatures prove N distinct attested
    agents approved the exact instruction. They do not prove the agents reasoned independently —
    distinct identifiers are checkable; independent reasoning is not.
